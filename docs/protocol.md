# A66 键盘 HID 配置协议（逆向笔记）

来源：A66 Keyboard 原厂 Windows 驱动 `OemDrv.exe`（SHA-256 `41f2642e8d4fea787e18038a09771db6fedefea43f44cdf55bec7dd0aace3631`），
2026-11-02 用 REA 6.8.0 + Ghidra 12.1.4 静态反编译；地址均为该文件的虚拟地址。
标注：**[观察]** = 直接读自代码/数据；**[推断]** = 由多处观察推出，尚未在设备上验证；**[未知]**。

本文是为了让 macOS 能配置这把键盘而整理的协议笔记，仓库里不包含原厂程序、配置文件或反编译代码。

## 1. 设备识别

| 项目 | 值 | 依据 |
|---|---|---|
| 有线 VID:PID | `0x258A:0x010C`（"BY Tech" / "Gaming Keyboard"） | [观察] macOS IORegistry + KB.ini |
| 无线 VID:PID | `0x3554:0xFA09`（KB.ini）；蓝牙实测 `0x3554:0xFA07` | [观察] |
| 固件类型 nFw | 24 (`0x18`) | [观察] KB.ini `Fw=24` |
| 配置接口 | Usage Page `0xFF00`、Usage 1、Feature 报告 520 字节 (`0x208`) | [观察] `CDevG5KB::FindHIDDevice` @0x485e10；macOS 描述符 Report ID 6 = 519 字节数据 + 1 字节 ID |
| 身份校验 | 读 6 字节"密码"与 KB.ini `Psd=3,0,0,0,0,D9` 比对，不符则放弃该设备 | [观察] @0x485e10 → @0x486890 |

同一 VID:PID 被 AULA / Redragon / Kreo / LEOBOG 等多家共用，**写入前必须先核对密码 = `03 00 00 00 00 D9`**。

## 2. 报文格式（`CDevG5KB::AccessData` @0x4861d0）

全部走 HID **Feature Report**，固定 520 字节：

| 偏移 | 含义 |
|---|---|
| 0 | Report ID：nFw==24 → `0x06`，否则 `0x09` |
| 1 | 命令字 |
| 2 | 子命令 / 区号（如层号） |
| 3 | 0 |
| 4 | 总分包数 = ceil(长度/512) |
| 5 | 当前包序号（从 0） |
| 6..7 | 本包数据长度，小端，≤ 512 |
| 8..519 | 数据 |

- 写：SetFeature(520 字节)。
- 读：SetFeature(包头) → 等待 → GetFeature(520 字节)，数据从偏移 8 取。
- SetFeature 失败重试 3 次，间隔 70 ms；每包前等待 20 ms（灯光直控 7 ms）。
- **读命令 = 写命令 | 0x80**。

## 3. 命令表

| 命令 | 方向 | 子命令 | 长度 | 用途 | 依据 |
|---|---|---|---|---|---|
| `0x82` | 读 | 1 | 6 | 设备密码/型号（末字节 `0xD9` = 型号） | [观察] @0x486890；与 OpenRGB 识别命令一致 |
| `0x03` | 写 | 层号 0–3 | 512 | **按键矩阵**（SetMatrix） | [观察] @0x486410，调用点 @0x4880a1 长度 = MatrixLen×4 |
| `0x83` | 读 | 层号 0–3 | 512 | **读回按键矩阵**：回包 = 包头原样回显 `06 83 层 00 01 00 00 02` + 512 字节（末尾 `00 00 5A A5`） | [实测 2026-11-03] 原厂驱动不用；按"读 = 写 \| 0x80"推出 |
| `0x04` / `0x84` | 写/读 | 0 | 128 | 灯效参数（SetLED/GetLED），写前先读 | [观察] @0x487e10 / @0x4864c0 |
| `0x05` | 写 | 0 | 宏缓冲区大小 | 宏数据（SetMacro） | [观察] @0x487e10 |
| `0x06` | 写 | 颜色组号 | 灯数×3 | 每键颜色（SetGame） | [观察] @0x487e10 |
| `0x08` / `0x88` | 写/读 | 0 | 可变 | 实时数据（灯光直控）；OpenRGB 用 `06 08 00 00 01 00 7A 01` + 378 字节 RGB | [观察]+OpenRGB |
| `0x0A` | 写 | 0 | 512 | 灯光颜色表（SetLedRgbTab），CRC 开启时含 `5A A5` 标记 | [观察] @0x487e10 |
| `0x0B` | 写 | 0 | 11 | SetScreenParam | [观察] @0x463690 |
| `0x0E` | 写 | 0 | 可变 | [未知] @0x486a70 | |

原厂驱动**不读回按键矩阵**（键盘类里没有 `0x83`），把键位存在电脑上（见 §6），整层写入。但固件支持 `0x83`：2026-11-03 实测，0–2 层读回与上次写入的内容逐字节相同，第 3 层为空（只有 `5A A5`），读完型号与键位均无变化。

## 4. 按键矩阵（命令 0x03）

- 每层 `MatrixLen` 项（KB.ini 未写，默认 `0x80` = 128），每项 4 字节 → 每层 512 字节，正好一包。
- 层：`LayerNum=4`；`LayerMask` 默认 0（4 层都写）。驱动只写"改动过"的层（dirty 位）。
- `CRC` 默认 1 → 每层最后一项（偏移 508）固定为 `0xA55A0000`（字节 `00 00 5A A5`）。 [观察] FillMatrix @0x4875e0
- 键在矩阵中的位置 = KB.ini `[KEY]` 每行最后一列（列优先、每列 6 格：Esc=1, Tab=2, Caps=3, LShift=4, LCtrl=5, `1`=7 …），范围 < 0x90。A66 的 67 个键见 `Sources/A66Core/Layout.swift`。
- 未定义的位置为 0。

### 设备码（4 字节，小端，`keyinfo_to_hardware_code` @0x486b80）

字节 0 = 类型：

| 类型 | 含义 | 字节 1..3 |
|---|---|---|
| `0x00` | 普通键/组合键 | [1] 修饰键位图（HID 标准：01 LCtrl,02 LShift,04 LAlt,08 LGUI,10 RCtrl,20 RShift,40 RAlt,80 RGUI），[2] HID(VK2)，**[3] HID(VK1) = 主键**（汇编 0x486d1a–0x486d88 核实；单键如 Esc = `00 00 00 29`，纯修饰键如左Ctrl = `00 01 00 00`） |
| `0x01` | 鼠标功能 | 如 `01 01 01 00` |
| `0x02` | 多媒体（Consumer） | [2..3] Consumer usage，高字节在前（`02 00 01 83` = 0x0183）：`00CD` 播放/暂停、`00E9` 音量+、`00EA` 音量−、`00E2` 静音、`00B5/B6/B7` 下一首/上一首/停止、`0192` 计算器… |
| `0x03` | 宏 | [1] 方式（1=按次数，2/4 其他），[2] 次数，[3] 宏编号 |
| `0x05`–`0x08` | 键盘自身功能（灯光、切换等） | KB.ini 中 `0x07xxxxxx`/`0x08xxxxxx` 原样 |
| `0x0D` | Fn 键 | `0D 00 00 00`（Fn2 = `0D 01 00 00`） |

- KB.ini / profile 里 `Major=9` 的条目是**按字节顺序书写**的设备码（驱动做一次字节序翻转）：`0x0700000b` → 字节 `07 00 00 0B`；Fn+1 的 `0x3a` → `00 00 00 3A`（普通键，HID F1）。
- 普通键由 Windows VK 码查表转 HID：表在 `0x5fda80`，112 对 (hid, vk)，查不到返回 0（导入 Windows 配置时用，见 `Sources/A66Core/WindowsImport.swift`）。
- Major=2 特例：修饰位为 0 且 VK1=`0xFA`/`0xFB` → Fn/Fn2；VK1=1–5（鼠标键）→ 直接用参数；VK1=`0x88–0x8F`、`0x99–0x9B` → 多媒体码。
- KB.ini `[KEY]` 解析（FUN_00411b40）：从 K1 起读到第一个缺号为止；第 5–7 列按十六进制、其余按十进制；修饰键（VK 0x10/0x11/0x12/0x5B/0x5C/0xA0–0xA5）存成修饰位、VK 清零。

## 5. 写入顺序（ApplySetting @0x487e10，nFlag 位）

`0x01` 键位+宏：FillMatrix → 逐个脏层 `0x03`（每包前 20 ms，层与层之间 Sleep(WaitTm)，Cfg.ini 未写时默认 30 ms）→ 有宏才发 `0x05`，前后无其他命令（FUN_00487a70 只是打日志）；`0x02` 灯效：`0x84` 读 → 改 → `0x04` 写；`0x40` 颜色表 `0x0A`；`0x10` 每键颜色 `0x06`。各步之间 Sleep（全局延时）。

## 6. 电脑端配置文件 profile.dct

`%LOCALAPPDATA%\BYCOMBO4\A66 Keyboard\profile.dct`（13312 字节）：
- 偏移 `0x3C` 起：4 层 × 144 条 × 16 字节键记录。
- 记录：`u32 (Major<<24 | Minor)`, `u8 修饰键`, `u8 VK1`, `u8 VK2`, `u8 _`, `u32 参数`, `u8 灯号`, `u8 矩阵号`, `u16 _`。
- **第 i 条 = KB.ini 的 K(i+1)**；记录里的矩阵号有时为 0，实际位置以 KB.ini 为准。
- Major：2 = 普通键（修饰键按位图存），9 = 原始设备码（参数），5 = 宏，其余见 §4。

## 7. 无线 / 蓝牙通道（CDev3632）

原驱动支持无线改键，传输层换成 `CDev3632`，上层仍走同一个 `CDevG5KB::ApplySetting`（同样的 4 层 × 512 字节矩阵）。

- **识别**（FUN_0040c020 / FUN_0046a260）：设备 VID:PID 必须等于 KB.ini 的 `VID_Wireless:PID_Wireless`（A66 写的是 `3554:FA09`），且有 Usage Page `0xFF02`、Usage 2、输入/输出各 20 字节的集合。[观察]
- **为什么 Windows 下蓝牙不识别**：蓝牙实测 PID 是 `FA07`（Karabiner 里还记录过 `FA08`），与 KB.ini 的 `FA09` 不符，驱动当作不支持的设备跳过。`FA09` 疑为 2.4G 接收器。[观察 + 推断]
- **报文**（FUN_00482c20），HID 输出报告 20 字节，报告 ID `0x13`：

| 偏移 | 含义 |
|---|---|
| 0 | `0x13` |
| 1 | 命令 |
| 2 | 总包数 = ceil(长度/14) |
| 3 | 包序号 |
| 4 | 高 4 位 = 子命令（如层号），低 4 位 = 本包数据长度 ≤ 14 |
| 5..18 | 数据 |
| 19 | 校验 = 字节 0..18 之和（取低 8 位） |

- 写命令（命令最高位为 0）每包都等键盘回 20 字节输入报告（FUN_00482840）：`[1]==命令` 为成功，`[0]==0xFF` 出错，`[2]&0x80` 校验错；超时/校验错最多重发 5 次。每包前延时 15 ms。
- 键位写入在无线下调用为 `AccessData(cmd=1, sub=层, data, 512, 重试=1, 延时=15ms)`（SetMatrix @0x486410 的 3632 分支，**已对汇编 0x48642f–0x486439 核实**）：512 字节分 37 包（36×14 + 8），每包等应答。
- 读命令（SendCMD_3632 @0x483530）：发 `13 命令 01 00 00 …0… 校验`，再收输入报告：`[1]&0x7F`=命令（最高位=校验错，重发）、`[2]&0x7F`=总包数、`[3]`=序号、`[4]&0x0F`=本包长度、`[5..]`=数据，收齐为止；每次收 1000 ms 超时。
- 识别流程（Watcher_Thread_3632，0x40baa0 起）：设备路径含 `pid&fa07` → 视为蓝牙（bBT）。非蓝牙（接收器）先发 `0x07` 读 1 字节，等键盘连上（收到 `[1]=0x0A,[6]=1`）；随后都发 **`0x05` 读 6 字节 = 密码**（蓝牙超时则每 1 s 重试）；之后 OnNewDongle 在蓝牙下**只按密码**匹配设备、不看 VID/PID。[观察]
- 无线命令表（与有线编号不通用）：`0x01` 键位、`0x02` 每键颜色、`0x03` 宏、`0x04` 灯效 128 字节、`0x09` 颜色表 512 字节、`0x88`/`0x8E` 实时数据（最高位置 1 = 不等应答，10 ms）、读：`0x05` 密码、`0x07` 连接状态、`0x44` 灯效（CDev3632::GetLED @0x482ed0，请求 `13 44 01 00 00 …`）。[观察]
- **无线读 = 写 + 0x40**（由 `0x04`/`0x44` 推出）。**读回按键矩阵 = `0x41`**：请求 `13 41 01 00 (层<<4) 0… 校验`，回 36 包 `13 41 24 序号 (层<<4|0E) 14 字节数据 校验` = 504 字节（比 512 少了末尾空项和 `5A A5` 标记；A66 的键都在前 384 字节）。2026-11-03 经 2.4G 实测，0–2 层与上次写入逐字节相同，第 3 层全 0；同一层偶尔第一次请求没有应答，重发即可（工具每层最多发 3 次，并核对序号连续、回显层号）。原厂驱动不用。[实测]
- **蓝牙读不了键位**（2026-11-03 实测）：固件对 `0x41` 有应答，但键盘约每 4 ms 发一包，蓝牙连接每 15 ms 只送出 1–2 包，其余被键盘丢掉（到达时间严格按 15 ms 一批，序号每批跳约 4）。回包节奏与连接事件对齐，每次丢的位置几乎相同（三层都总缺第 1、2、3、6、10、14、18、22 包），8 次请求按序号合并也只凑到 26–29/36 包。所以蓝牙下不读键位、写入后不做读回核对（写入逐包应答，不受影响）。
  - 丢包在键盘一侧，不在 Mac 一侧：把 macOS 的输入报告缓冲调到 64 条（`IOHIDDeviceSetProperty` 设 `MaxReportBufferCount`），到达情况不变，仍是每 15 ms 一包、偶尔两包，序号 0、4、8、12…。看起来键盘只留 1 包待发，等发送时机的这段时间里新生成的包直接丢掉；第 0 包生成后要等约 15 ms 才能发出，期间生成的第 1–3 包每次都丢，主机这边补不回来。[推断，较强]
  - **PacketLogger 抓包定案**（2026-11-03，装苹果官方 Bluetooth Logging 描述文件后抓 HCI）：配置通道是 GATT 句柄 `0x001F`（写请求，带写响应）/ `0x001B`（通知），抓包里能看到内容。两次 `0x41` 读取，Mac 蓝牙芯片收到的通知分别是序号 0,4,8,11,15,16,19,23,27,31,35 和 0,4,8,12,16,20,24,27,28,32,35，各 11 包，**与程序收到的逐一相同**；通知间隔 15 ms（偶尔同一连接事件 2 包）。BLE 链路层有确认重传，芯片没收到就是键盘没发出来 → 包丢在键盘固件里，主机侧无法补救。[实测]
  - 硬件结构 [推断，较强]：同类三模键盘是"中颖 8051 主控（USB 258A）+ 博通集成 Beken BK3632 无线芯片"，两者用软件模拟的 SPI 通信，帧格式 `AA 长度 命令 … 校验`；无线芯片收下一帧会翻转一根 ACK 线（开源固件 [smk](https://github.com/carlossless/smk) 的 `src/peripherals/bk3632/`，以及 smk issue #7）。A66 部分吻合：原厂驱动无线类名 `CDev3632`；蓝牙名 "A66 5.0 " / "A66 3.0" 符合主控启动时给无线芯片设"板名 + 5.0 / 3.0"的做法。但 2.4G 接收器的 USB 厂商字符串是 "Compx"（`3554` 疑为其 VID），键盘里的无线芯片是 BK3632 还是 Compx 的芯片 [未知]。smk 没有实现原厂配置通道（报告 0x13），BK3632 固件闭源、无公开资料，所以查不到读回包到底是主控没等 ACK，还是无线芯片只留一包。要核实只能反汇编 A66 原厂固件（需 dump，不做）。
  - **经典蓝牙（"A66 3.0"，`3554:FA08`）可以读**（2026-11-03 实测）：键盘同时广播低功耗蓝牙 "A66 5.0"（FA07）和经典蓝牙 "A66 3.0"（FA08），后者配置通道相同（FF02:2，报告 0x13）。经典蓝牙下每次请求也只到 13–17/36 包，但缺的位置每次不同，按序号合并多次请求能凑齐：0–2 层分别请求 19、26、12 次（10.2 / 15.0 / 6.2 秒），与上次写入记录逐字节相同（只有测试时手动改过的矩阵 92 不同）。空闲后读密码要 7–15 秒才应答。Karabiner 接管该设备时同样 0xE00002C5。
  - 请求里的字节 3/4/5/6 怎么改，回包都从第 0 包、键位表开头发起，没有分段 / 偏移参数。[观察]
- **读灯效 `0x44`**（2026-11-03 经 2.4G 实测）：请求 `13 44 01 00 00 0… 58`，回 10 包共 128 字节（末尾 `5A A5`），格式与实测结果见 §10。
  - 收到的包内容是对的：蓝牙读回的矩阵 92（Del）是 `0x51`（↓），一开始以为是读错，后来确认是测试时手动改的，键盘里存的就是 ↓。[观察]
- 无线版 ApplySetting（@0x483930）：Sleep 200 ms → 在内存里构造临时 CDevG5KB（FUN_00485d20，不发命令）→ 走同一个 ApplySetting → Sleep 50 ms。没有额外的"进入配置"命令。
- **2026-11-02 Mac 蓝牙实测**（`a66 identify --bt`）：发 `13 05 01 00 00…00 19` → 回 `13 05 01 00 0A 03 00 00 00 00 D9 00 00 10 00 … 0F`（10 字节，前 6 字节 = 密码，后 4 字节 `00 00 10 00` 含义 [未知]）。另收到键盘主动发的 `13 0A 01 00 04 05 64 10 00 … 9B`（命令 0x0A，接收器流程里用作"已连接"判断；`64`=100 = 电量百分比：同时刻 macOS `system_profiler SPBluetoothDataType` 经蓝牙标准电池服务读到 A66 "Battery Level: 100%"，一个数据点吻合 [推断，较强]）。首个请求超时、重发后应答，与原驱动蓝牙下每秒重试一致。两种回包的校验和规则与发送相同。
- **2026-11-02 Mac 蓝牙写入实测通过**：`apply --bt --layers 0 --factory K16 --yes`（该键变 PgUp）→ `apply --bt --yes`（0–2 层各 37 包全部应答，未重发）→ 实机确认键位按写入生效。蓝牙写入的是与有线同一份键位表，子命令高半字节 = 层号有效。空闲后读密码要等 2–8 秒才有应答（重发 1–4 次），工具已设最多 10 次。
- **2026-11-03 2.4G 接收器实测**：接收器 `3554:FA09` "2.4G Wireless Receiver"（= KB.ini `PID_Wireless`），配置通道与蓝牙相同（FF02:2，输出报告 20 字节）。读密码回包与蓝牙完全相同；单键测试与 0–2 层整表写入均逐包应答，空闲后头两个请求无应答、第三次应答。没有发原驱动接收器流程里的 `0x07`（连接状态），直接读密码即可。
- macOS 上蓝牙配置通道与键盘本体是同一个 HID 设备：需要"输入监控"权限，且 Karabiner 若接管该设备会独占（`kIOReturnExclusiveAccess`）。2.4G 下配置通道在 USB 接收器上，实测 Karabiner 接管时也能打开（同样需要输入监控权限）。
- 有线配置接口同样需要"输入监控"：IOKit 里有线、2.4G 的配置接口都标着 `RequiresTCCAuthorization = Yes`（2026-11-03 用 ioreg 核实），因为接口里同时有键盘、鼠标集合，macOS 按整个接口要求授权。Chrome WebHID 也受此限制，给 Chrome 授权后可正常打开（2026-11-03 实测）。

**说明书有、键位表里没有的**（固件自行处理，4 层键位表不体现，至少 KB.ini 未定义）：

- 机身拨动开关：Mac/Win 系统切换、蓝牙/有线/2.4G 三模切换。

## 10. 灯效设置块（有线 `0x84` 读 / `0x04` 写，128 字节；无线 `0x04` 写）

ApplySetting 的 nFlag&2 分支：先读 128 字节 → FUN_00487b20 按配置改写部分字节 → 整块写回。已识别的字段 [观察，含义部分为推断]：

| 偏移 | 内容 |
|---|---|
| 3 | 某开关（配置 +0x2d48 非 0 时写 profile+0x3340） |
| 9 | 当前灯效是否为"高手键"灯效（GaoshouIndex=18） |
| 10 | **当前灯效（硬件编号）**，来自 KB.ini `LedOptN` 映射表 |
| 11 | 颜色组 = StartGp(0x20) + 组号 |
| 0x16 | profile+0x3338（疑为休眠时间） |
| 0x17 | 配置 +0x2d68==1 时写入的开关（疑为自动识别系统） |
| 0x18 | 来自配置 +0x2e1c 表（疑为按键去抖档位，A66 `ShowDebounce` 开启） |
| 0x1a | 旋钮模式（nWheelMode） |
| 0x32–0x35 | 侧灯（A66 无） |
| 0x38, 0x39 | 固定 `FF FF` |
| 0x3a + 2i | 第 i 种灯效的亮度（LightHW 映射值） |
| 0x3b + 2i | 第 i 种灯效：低 4 位颜色、高 4 位速度（SpeedHW） |

**2026-11-03 实测确认**（2.4G 下 `0x44` 读，在键盘上逐项调灯光、每次读一遍对比；原厂驱动 CDev3632::GetLED 用的同一命令）：
- `[10]` 随 Fn+\ 每次 +1（12→13），确为当前灯效编号。原厂文件里只有编号、没有名称。
- 第 N 种灯效的设置在 `0x3A + 2×(N−1)`：亮度 0–4（4 最亮；Fn+↑ 已在最高档时不变，Fn+↓ 两次 4→2），速度在第 2 字节高 4 位（Fn+← 两次 4→2），颜色在低 4 位（Fn+Enter 一次 7→0；目测 7 = 彩色、0 = 红色，1–6 [未知]）。每种灯效各存一份，互不影响。
- 键盘用 Fn 组合键改灯光后，读回立即反映。连读两次结果相同。有线读命令 `0x84` 未实测；蓝牙下 10 包按 4 ms 发，预计同样会丢。

**没有"哪些灯效参与 Fn+\ 循环"的字段**，循环列表由固件决定。KB.ini `LedMask` 与灯效无关（控制界面按键指派树里隐藏哪些功能分类）。设备码 `00 00 00 00` = 驱动界面的"无功能"（Major 8 子码 0xA2 → 0）。
